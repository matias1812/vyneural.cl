Código abierto

Todo lo que hace Vyneural —la web, las simulaciones y el shell Android— está publicado en GitHub. Podés revisar el código, ver cómo se construye la APK y verificar por ti mismo qué hace (y qué no hace) la aplicación.

Ver el repositorio en GitHub →

Un solo repositorio, tres piezas

El proyecto vive en github.com/matias1812/vyneural.cl. No es una caja negra: cada pieza tiene su código fuente y su documentación.

  • Web y PWA: generador de ondas binaurales en tiempo real con Web Audio API (Vite, JavaScript puro, sin frameworks).
  • Núcleo científico: la simulación matemática, los modelos de estados y la reproducción de experimentos, separados de la interfaz para poder verificarlos.
  • Shell Android: la app (Kotlin + WebView) que envuelve la misma web con capacidades nativas: audio en segundo plano, controles en pantalla bloqueada, notificaciones y alarmas reales.

El núcleo de la web y el de la APK es exactamente el mismo código: la app no tiene lógica aparte, solo una capa nativa que la web no puede ofrecer.

¿Por qué código abierto?

Una herramienta de relajación no debería exigirte fe ciega. Si vas a ponerle audífonos y dejarte llevar, lo mínimo es poder comprobar qué está sonando y adónde van tus datos: a ningún lado.

  • Verificable: podés leer el código y confirmar que el audio se genera localmente, sin backend ni telemetría.
  • Reproducible: la APK se construye con los pasos publicados; podés compilar la tuya y comparar el SHA-256.
  • Sin sorpresas: sin cuentas, sin anuncios, sin rastreo. El repositorio lo demuestra.
  • Mejorable: si encontrás un bug o se te ocurre una idea, el código está ahí para que la propongas.

Compilalo vos mismo

La web se compila con Vite y la APK con Gradle. Los pasos exactos están en el README del repositorio; en esencia son dos comandos: 

npm install
npm run build        # → web en dist/
cd android
./gradlew assembleRelease   # → APK firmada

La firma de la APK que se distribuye usa un keystore propio del proyecto que nunca se sube al repositorio: por eso conviene verificar el SHA-256 publicado en la página de descarga contra el archivo que recibís.

¿Cómo contribuir?

Hay muchas formas de aportar, y casi todas empiezan por una conversación:

  • Reportá un bug con un issue: qué hiciste, qué esperabas y qué pasó.
  • Proponé una mejora: un estado nuevo, un ambiente, una visualización.
  • Enviá un pull request con el cambio explicado; se revisa con la misma honestidad con la que está escrito el código.
  • Compartí el proyecto: la mayor contribución es que alguien más lo use y lo verifique.

¿Preferís hablar antes de escribir código? Abrí un issue en el repositorio.
